# Docs as Code Without Leaving Writers Behind: Two-Way GitHub Sync With Document360 Lotus

## Why docs as code keeps splitting teams in two

Docs as code is simple to describe: keep documentation in the same repository as the product, write it in Markdown, and review it with pull requests. Developers love it. Docs ship with the code, every change has a reviewer, and history lives in Git.

The trouble starts with everyone else. Technical writers, product managers and support leads don't want to clone a repo to fix a typo. So teams end up with two copies of every doc: Markdown in GitHub for the developers, and a pasted version in the knowledge base for customers. The two drift apart a little more with every release.

The fix isn't choosing one camp. It's keeping one source of truth that both camps can edit, in the tool each already uses.

## What docs as code needs to work for a whole team

A docs-as-code setup that works for the whole team does five things:

1. **Syncs both ways.** A commit in GitHub shows up in the editor, and an edit in the editor shows up in GitHub.
2. **Brings Git to the browser.** Branches, commits and pull requests without a terminal.
3. **Makes conflicts readable.** When both sides change the same paragraph, a writer can choose without reading merge markers.
4. **Fits existing repos.** Any branch, docs in a subdirectory, and a clear way to describe structure.
5. **Publishes to a real knowledge base.** Search, navigation, AI answers and localization, not just a static site.

## How Document360 Lotus does docs as code

Lotus is Document360's docs-as-code experience. Your docs live in a GitHub repository and stay in sync with Document360 in both directions.

![Lotus keeps GitHub and Document360 in sync both ways](img:herobare)

### Connect a repository in minutes

Choose **Document360 Lotus** when you create a project, authorize GitHub and install the Document360 GitHub App. Pick any repository and branch; if your docs live in a subdirectory, point Lotus at it. Lotus looks for a `d360.json` manifest that maps folders to categories and files to articles.

![Connect with GitHub](img:connect)

### Let your coding agent write the manifest

No `d360.json` yet? Lotus gives you a prompt to paste into Claude Code, Cursor or Codex. The agent finds your Markdown, builds the manifest, commits it, and you click re-check. Prefer a head start? Start from a template, and Lotus commits sample content and the manifest for you.

### Edit anywhere, sync everywhere

After the first sync, developers keep committing to GitHub and writers edit in Document360. The top bar always shows where things stand: Synced, Syncing, Updates waiting, or Sync failed.

### Branches and pull requests, from the editor

Create a working branch, save your changes to it as a commit, and open a pull request without leaving Document360. When the pull request is ready, **Merge & publish** merges it and publishes the docs in one step.

![Pull request ready to merge](img:prmenu)

### Conflicts you can actually resolve

When a commit and an edit touch the same article, Lotus shows each conflict side by side. Keep GitHub's version, keep yours, or keep both, then mark the article resolved. While someone is resolving an article, it's locked so no one overwrites their work.

![Review conflicts](img:conflicts)

### Publish with a safety net

Every publish starts with a full list of what changed: articles, snippets, glossary terms, variables and tags. Auto Fix suggests SEO descriptions, tags and related articles for the pages you changed, and everything goes out in one commit.

### No GitHub account needed for writers

Writers and product managers never need a GitHub account. What they can edit, save, publish or merge follows their Document360 role, and GitHub permissions never grant access in Document360. If the main branch is protected, publishing opens a pull request so your review rules still apply.

### Every change on the record

Link your GitHub account, and your Document360 publishes are committed under your own GitHub account, while commits you make in GitHub are credited to you in Document360's audit log and as a contributor on the knowledge base site. The audit log records pushes, branches, pull requests and merges, with the files each one changed.

## Frequently asked questions

**What is docs as code?**
An approach where documentation lives in a version-controlled repository, is written in plain text such as Markdown, and goes through the same review process as code.

**Can non-developers work in a docs-as-code workflow?**
Yes, if the platform syncs both ways. With Lotus, writers edit in Document360, and Lotus turns their work into commits and pull requests.

**What is d360.json?**
A manifest in your repository that maps folders to categories and Markdown files to articles. Your coding agent can generate it from a prompt Lotus provides.

**How is Lotus different from Document360's GitHub extension?**
The extension syncs one way, from the main branch of GitHub into Document360. Lotus syncs both ways, on any branch, with branches, pull requests and conflict resolution in the editor.

**Does Lotus work with GitLab or Bitbucket?**
Lotus launches with GitHub. Other providers are not supported yet.
